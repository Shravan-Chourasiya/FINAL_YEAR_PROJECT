# Database Conventions

Status: **Locked for Phase 1.** These conventions apply to every table in
`backend/`. A new table must follow every rule below; it does not get to
invent its own ID strategy, timestamp behavior, naming style, transaction
boundary, or deletion policy. If a future requirement genuinely can't fit
one of these rules, that's a reason to open a discussion and amend this
document — not to quietly diverge in a migration.

This document does not describe HTTP routes, controllers, or business
logic. It only describes what the data layer looks like on disk (schema/
migrations) and how the application is allowed to talk to it.

> **Architecture note:** an earlier draft of the backend planned a
> `repositories/` layer (base repository class, per-entity repository
> classes, repository inheritance). **That plan has been discarded.** The
> current backend structure is:
>
> ```
> backend/src/
> ├── controllers/
> ├── schemas/
> ├── routes/
> ├── modules/
> ├── middlewares/
> ├── config/
> ├── db/
> ├── services/
> ├── utils/
> ├── types/
> └── server.ts
> ```
>
> Anywhere this document or an older doc says "repository," read it as
> "the data-access code living under `services/` (backed by `db/`)."
> There is no `repositories/` directory, no base repository class, and no
> repository inheritance anywhere in this codebase. Data access is plain
> functions in `services/`, built on top of whatever the project's
> ORM/query builder exposes from `db/`.

## 1. ID Strategy

**Decision: every table's primary key is a `UUID`.**

```sql
id UUID PRIMARY KEY
```

Do **not** use `SERIAL` / `BIGSERIAL` / integer auto-increment primary keys
on any Phase 1 table, and do not mix ID strategies across tables.

### Why UUID

- Non-sequential — IDs don't leak record ordering or approximate row counts
  to clients.
- Safer to expose directly in URLs/APIs than an incrementing integer.
- Avoids ID-guessing/enumeration issues.
- Plays well with distributed/application-generated inserts (no need to
  round-trip to the DB to learn the new ID before doing related work).
- One strategy, used everywhere, means no table-by-table judgment calls.

### Generation mechanism

**UUIDs are generated by PostgreSQL, at the column default — not by
application code.** Use the column default so `INSERT` statements that
omit `id` still get a valid UUID from the database:

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

`gen_random_uuid()` (from PostgreSQL's built-in `pgcrypto`/core, Postgres
13+) is the chosen generator. Do not introduce `uuid-ossp`'s
`uuid_generate_v4()` alongside it — pick the one already enabled in the
project's Postgres image and use it consistently; if `pgcrypto` isn't
enabled yet, enable it once in a migration:

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

Application code (`services/`) must never generate the primary-key UUID
itself (no `crypto.randomUUID()` for PKs). The database is the single
source of truth for ID generation, matching the timestamp rule below.

### Foreign keys

Any column referencing a UUID primary key is itself `UUID` — never cast or
store it as text.

```sql
user_id UUID NOT NULL REFERENCES users(id)
```

## 2. Timestamp Strategy

**Decision: every table has `created_at` and `updated_at`, both
`TIMESTAMPTZ`, both generated and maintained by the database.**

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

### UTC

`TIMESTAMPTZ` stores instants normalized to UTC internally regardless of
session time zone; treat every timestamp coming out of the DB as UTC.
Application code formats/localizes for display — it does not decide what
"now" was.

### Database-generated, not application-generated

- `created_at` is set once, by `DEFAULT NOW()`, at insert time.
- `updated_at` must be advanced automatically **by Postgres** whenever a
  row changes — not by the application setting `updated_at = new Date()`
  in a service function.

Application code (`services/`, `controllers/`) must never write to
`created_at` or `updated_at` directly.

### `updated_at` auto-update mechanism

`DEFAULT NOW()` only covers the initial insert; it does nothing on
`UPDATE`. Use one shared trigger function, applied to every Phase 1 table,
so this behavior is centralized instead of hand-rolled per table:

```sql
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

Then, per table:

```sql
CREATE TRIGGER trg_<table_name>_set_updated_at
BEFORE UPDATE ON <table_name>
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();
```

Every Phase 1 migration that creates a table must also create this
trigger on that table (the function itself is created once, in the first
migration that needs it, and reused everywhere after).

## 3. Naming Conventions

### Database layer (SQL / migrations)

- **snake_case** for table names, column names, foreign keys, indexes, and
  constraints. No camelCase or PascalCase anywhere in the schema.
- **Table names are plural**: `users`, `sessions`, `interviews`,
  `user_interview_history`, `user_interview_metrics`.
- **Foreign key columns** follow `<singular_entity>_id`:
  `user_id`, `session_id`, `interview_id`.
  Never `userId`, `usersId`, `user`, or `interviewId` in SQL.

### Application layer (TypeScript)

TypeScript stays **camelCase**, independent of the DB's snake_case. The
mapping between the two layers happens once, at the `db/`/`services/`
boundary (query result mapping / ORM column mapping) — it is not
re-invented per controller.

| Database (`db/`, SQL) | TypeScript (`types/`, `services/`, `controllers/`) |
|---|---|
| `user_id`             | `userId`                                            |
| `created_at`          | `createdAt`                                         |
| `updated_at`          | `updatedAt`                                         |
| `disabled_at`         | `disabledAt`                                        |

Keep the two naming worlds clearly separated: SQL/migration files never use
camelCase, and TypeScript types/interfaces never use snake_case field
names.

## 4. Transaction Strategy

**Decision: transactions are opt-in per business operation, not automatic
per query.** A transaction wraps a business operation only when that
operation performs multiple writes that must all succeed or all fail
together to leave the data consistent.

### Operations that must be transactional (Phase 1 scope + near-term)

1. **Registration** — user creation + initial session/token state.
2. **Token refresh** — session/token rotation + invalidation of the
   previous token/session.
3. **Forgot password** — password-recovery state + reset-token creation.
4. **Password reset** — password update + reset-token invalidation +
   related session invalidation (where required).
5. **Email update** — email change + verification-state change.
6. **Login with 2FA** — authentication state + session creation/update.
7. **2FA setup** — 2FA configuration + activation/verification state.
8. **Account deletion/deactivation** — account lifecycle state change +
   associated security/session state change.
9. **Account recovery** — account restoration + related
   lifecycle/security state.
10. **Interview creation** (future) — interview row + any required
    initial related records.

General rule: if two or more writes represent one logical business
operation, they run inside one transaction. A single-row write (e.g. "read
a user by id") never needs one.

### Where the transaction boundary lives

There is no repository layer, so there's no repository "transaction
manager" to build. The transaction boundary is owned by **`services/`**,
using whatever transaction primitive the project's chosen DB
client/ORM exposes (e.g. a `withTransaction(db, async (tx) => { ... })`
helper in `db/`, or the ORM's native transaction API). A service function
that implements one of the operations above:

1. Opens a transaction via the shared `db/` transaction helper.
2. Performs each write against the transactional client/handle it was
   given (not a fresh top-level connection).
3. Commits on success, rolls back on any thrown error.

Conceptually:

```
BEGIN
  <write A>
  <write B>
  <write C>
COMMIT   -- or ROLLBACK if any write throws
```

Controllers never open transactions directly — they call a service, and
the service decides whether the operation needs one. Nested, independent
transactions for individual writes that belong to the same business
operation are not allowed; there is exactly one transaction per business
operation, containing every write that operation needs.

## 5. Soft-Delete Policy

**Decision: soft delete is not a global convention.** It is decided per
entity, based on actual product requirements — most Phase 1 tables get no
soft-delete column at all.

- **Default for Phase 1 tables** (sessions, interview records, metrics,
  history, etc.): no `deleted_at` column. If/when one of these entities
  needs its own retention or recovery behavior, that is decided
  independently for that table, on its own merits — it is not inherited
  automatically from the users policy below.
- **`users` is the one entity with a defined lifecycle requirement**,
  described next. Do not add `deleted_at` to every table just because
  `users` has a 30-day recovery window — that would be exactly the kind of
  invented, table-by-table inconsistency this document exists to prevent.

### User account deletion / recovery lifecycle

When a user requests account deletion:

1. The account is marked **disabled/deactivated** — it does not disappear
   immediately.
2. User data remains stored for a **30-day recovery window**.
3. During those 30 days, the account can be **recovered** (reversing the
   disable and clearing the scheduled deletion).
4. The account has a **scheduled permanent-deletion timestamp** set at the
   moment of the deletion request (request time + 30 days).
5. After the 30-day window elapses, the account and its applicable
   associated data are **permanently deleted** from the database (a hard
   delete, not a flag flip).

This is represented on `users` with lifecycle columns rather than a bare
`deleted_at` flag, since the state machine has more than two states
(active → disabled-but-recoverable → permanently gone):

```sql
account_status         TEXT NOT NULL DEFAULT 'active'
                        CHECK (account_status IN ('active', 'disabled', 'deleted')),
disabled_at             TIMESTAMPTZ,
scheduled_deletion_at   TIMESTAMPTZ
```

- `account_status = 'active'`, `disabled_at`/`scheduled_deletion_at` both
  `NULL` — normal account.
- `account_status = 'disabled'`, `disabled_at` set,
  `scheduled_deletion_at` = `disabled_at + interval '30 days'` — inside
  the recovery window.
- Recovery clears `disabled_at` and `scheduled_deletion_at` and resets
  `account_status` back to `'active'`.
- Once `scheduled_deletion_at` has passed, a cleanup process performs the
  actual hard delete of the row (and any associated data whose lifecycle
  is tied to the account), then the row is gone — `account_status =
  'deleted'` is not a long-lived resting state, it's only relevant
  transiently if deletion is processed asynchronously rather than
  in-line.

This policy lives on `users` only. It is an account-lifecycle policy, not
a schema-wide soft-delete system.

## 6. Summary Checklist (for every new Phase 1 table)

- [ ] `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- [ ] `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
- [ ] `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
- [ ] `updated_at` trigger (`set_updated_at()`) attached to the table
- [ ] Table name is plural, snake_case
- [ ] Column names are snake_case
- [ ] Any foreign key is `UUID` + `<entity>_id` + `REFERENCES <table>(id)`
      with an explicitly chosen `ON DELETE` behavior (never a default
      CASCADE applied without thinking about the entity's lifecycle)
- [ ] No `deleted_at` added unless this specific entity has a documented
      product requirement for it
- [ ] Any multi-write business operation touching this table is wrapped
      in a `services/`-owned transaction, not left as separate writes
- [ ] Corresponding TypeScript types in `types/` use camelCase; mapping to
      snake_case happens at the `db/`/`services/` boundary, nowhere else
